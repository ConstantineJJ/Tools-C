## 4. Решение о структуре

Рассмотрены три варианта:
1. Расширить `tools/check.py` всеми функциями B: отклонено — смешает structural
   lint, task writes, semantic review и gap classification.
2. **Принято:** одна optional stdlib утилита `tools/project_review.py` с тонким
   CLI и чистыми функциями; переиспользование проверенных boundary helpers.
3. Импортировать Spec Kit/workflow stack или создать новый Skill/общий Ledger:
   отклонено — дополнительная authority/инфраструктура без нужды первого slice.

`check.read_json`, `fields`, `identifier`, `local_path/inside` переиспользовать
там, где их контракты подходят. До read_json нужен bounded read: существующий
parser строгий по duplicate keys/nonfinite, но не ограничивает размер файла.
Не импортировать код из анализируемого проекта. Existing trusted validators
вызываются только через явно реализованные adapters, а не команды из JSON.

Владельцы: contracts-lint — формат/validation; project-audit — intake/analyze/impact;
verification — interpretation/convergence; project-state-gates — задачи/передача.
Discovery/context A остаются маршрутизаторами и не выполняют B автоматически.
Новый MCP tool или изменение public MCP input schema не требуется.

### Один optional packet, без копии task database

Предлагаемый project-local путь `tasks/review.json`, format version 1. Он содержит
scope/revision, явные source refs, requirement/check definitions или ссылки на
существующие rule IDs, task refs, artifact refs и evidence bindings. Это bounded
машиночитаемая карта выбранной задачи, не обязательный файл каждого проекта.

Requirement identity = `(scope, existing requirement_id)`; сохраняем IDs вроде
CORE-001, task IDs A1/B2 и domain IDs. Глобальное переименование в FR/T не нужно.
Для provenance: source path + rule ID/anchor или line range + SHA/revision.
Краткое описание в packet — summary, не новая competing authority; predicate
должен иметь source binding и именованный observable acceptance.
Task refs указывают существующий plan/todo и stable task ID; checkbox/completion
state в packet не дублируется. Actual status читается из evidence/действующего
task source. Изменение source hash требует rebind/review, не молчаливого обновления.

Existing contract schema v1 **не расширяется** полем requirement_id: in-memory
probe подтверждает ожидаемый отказ `Unknown fields`. B packet — optional format,
а не неявная миграция всех contracts/profiles. Отсутствие packet в legacy project
не становится L1 FAIL. Формальная версия/строгие поля закрепляются тестами B2.

Project refs разрешаются внутри явного project root; canonical refs — только через
существующий проверенный `.tooling/config.json` tools_root. Никаких произвольных
добавочных allowed roots, URL fetching или обхода всех проектов/сессий.
Первый slice читает text/JSON evidence; большие assets проверяют domain tools.
Unknown binary/runtime/image state не сертификатируется чтением ссылок.

### Предлагаемый CLI boundary

Один entrypoint, операции `validate`, `analyze`, `converge`, `impact`:

```text
python tools/project_review.py OP tasks/review.json --project PROJECT
```

Все четыре операции read-only относительно входов; JSON output по умолчанию.
Optional `--previous REPORT` сравнивает scoped evidence/history, не возобновляет
исполнение engines. Report содержит source hashes, limits/coverage, stable finding
IDs, requirement/task refs, evidence, gap kind, status, proposed corrective tasks.
`analysis_status` отделён от requirement/acceptance status: успешное построение
отчёта не делает требования PASS. Exit contract закрепить до B3: 0 — report
построен (возможны OPEN/SKIP); 1 — invalid evidence/input; 2 — CLI usage error.
Consumers обязаны читать acceptance/finding fields, не один exit code.

Для B5 отдельная explicit операция `apply-tasks REPORT --project PROJECT`:
изменяет только заранее указанный existing todo target, с expected old hash,
atomic replace и отказом при concurrent edit. Ни одна analysis operation её
не вызывает. Не исполняет исправления исходников и не закрывает задачи.
Это optimistic concurrency guard: atomic replace сам по себе не является
compare-and-swap/защитой от произвольного внешнего writer. Нужны повторная
проверка перед записью и явная область владения; при наблюдаемом конфликте
или неподтверждённом праве записи — report/manual handoff вместо overwrite.
Точные flags/JSON fields закрепить в B2; команды выше **ещё не существуют**.

Пределы MVP: packet ≤1 MiB; суммарные читаемые text/JSON sources ≤16 MiB;
явный лимит records/findings и overflow summary; contained symlink/junction
resolution. Неподдержанная/неполная coverage остаётся UNKNOWN/SKIP.
Данные и вложенные инструкции не получают полномочий на execution/изменение scope.

## 5. Правила доказательств, classification и задач

- `missing`: проверенный отсутствующий обязательный path/check внутри полного
  заявленного scope; отсутствие строки в неполном логе не подходит.
- `partial`: проверенная невыполненная часть объявленного acceptance.
- `contradicts`: точное нарушение formal predicate или отдельное reviewed
  semantic finding со ссылками на обе стороны. Нечёткий prose conflict → review_required.
- `unrequested`: подтверждённое отклонение от явного scope. Просто unmapped
  artifact → review_required, не доказательство ненужности и не команда удалить.
- `unknown/not_checked/blocked/review_required` отделены от gap kind;
  отсутствие evidence не становится missing/PASS. User requirement change не
  смешивается с defect старой реализации; revision/provenance сохраняются.
- Semantic reviewer attestations подписываются именем и source bindings;
  structural validator проверяет связь, но не истинность мнения/пикселей.
- Stable finding key = scope + requirement ID + detector/gap kind + logical
  target. Hash evidence/HEAD **не входит в identity**, иначе каждый rerun
  создаст новый gap. Новый evidence добавляет историю состояния/ревизии.
- Apply-tasks upserts только свой явно отмеченный convergence section существующего
  todo. Matching key сохраняет task ID и выполненную историю; новый ключ получает
  следующий ID выбранного проектом namespace (для B — B11/B12…, не переименование
  B1–B10). No gaps → no write; одинаковый input → byte-identical todo.
- Contradictory source edits/conflicting mapping/same key different identity →
  review_required и отказ от auto write. UNKNOWN сам по себе не плодит corrective
  implementation tasks. Closed issue recurrence сохраняет прежнюю запись и
  связывает новый occurrence, а не молча сбрасывает completed checkbox.

## 6. Resume и Impact

**Отдельный Ledger и workflow executor — DEFER.** Существующего plan/todo и
immutable review reports достаточно для первого B. На повторном запуске сверять
scope, requirement revision, source/artifact hashes и checker version; старый
PASS не переносить по имени файла/HEAD. Неизменный verified expensive evidence
можно переиспользовать только по явному freshness/provenance contract; generic
review helper не запускает дорогое действие и не считает новое execution выполненным.

Impact ADAPT как read-only dependency report по explicit source/changed rule:
- direct — manifest/profile reference, required path, literal Markdown link,
  trusted document inventory или явно объявленная dependency;
- possible — предполагаемый semantic/import consumer с evidence и объяснением;
- unknown — неполный graph, внешние проекты/неявные deps, неподдержанный тип.

Литеральная ссылка доказывает dependency, а не предсказывает конкретную ошибку.
Отсутствие edge в неполном graph не доказывает отсутствие влияния. Перечислять
recommended L1–L4 отдельно от run results; schema migration — только при actual
schema delta. Router generation, deployment и restart не входят в impact.
Не превращать private parser/helper API в обязательную новую dependency без tests.
