## 2. Подтверждённые находки

### AB-01 — P2: B теряет повторный дефект после исправления

**Где:** [project_review_tasks.py](tools/project_review_tasks.py), строки 98–99 и 151–154; [project_review.py](tools/project_review.py), `observation_digest` и `convergence`.

**Воспроизведение на реальных временных файлах:**

1. В packet обязательный результат отсутствует. `converge` даёт FAIL, `apply-tasks` создаёт B11 в отдельном существующем `fixes.md`. Исходная задача привязана к `plan.md`; оба файла допустимы по текущему интерфейсу.
2. Результат создаётся; следующий `converge --previous first.json` даёт PASS и `not_observed` для прежнего finding. B11 явно отмечается выполненной.
3. Результат снова удаляется. Packet, исходные документы и revision не меняются: изменилось именно проверяемое состояние артефакта.
4. Следующий отчёт честно содержит историю `FAIL → not_observed → FAIL`, но `apply-tasks` отвечает `written=false, reason=already_recorded`. Открытой задачи нет; остаётся только закрытая B11.

**Причина:** проверяется совпадение `state_sha256` с любой исторической записью, включая закрытые задачи. Повторное появление прежнего состояния ошибочно считается повторной отправкой старого отчёта. Промежуточное исчезновение дефекта уже есть в `--previous`, но writer его не учитывает.

**Последствие:** проверка результата остаётся FAIL, однако список исправлений может выглядеть закрытым. Это не ложный PASS самого `converge`, а потеря корректирующей задачи.

**Как исправить:** различать повторную подачу того же наблюдения и новую последовательность наблюдений. Использовать нормализованную историю конкретного finding, включая переход через `not_observed`, либо явный идентификатор occurrence; не ограничиваться хешем текущего состояния. Обновить обе ветки дедупликации. При доказанном повторном появлении создавать B12 с `previous=B11`, сохраняя закрытый checkbox B11. Без истории перехода не выдумывать новое событие; при необходимости требовать явную новую revision. Отдельный Ledger не нужен.

**Критерий приёмки:** тест `FAIL → PASS → FAIL` с тем же packet/revision, отдельным todo и закрытой первой задачей создаёт связанную новую задачу; повторная подача последнего отчёта остаётся NO-OP. Дополнительно проверить `A → B → A` для наблюдений открытой задачи и сохранить существующие проверки блокировок/атомарной записи.

### AB-02 — P2: B может закрыть acceptance при усечённых findings

**Где:** [project_review.py](tools/project_review.py), строки 297–314, особенно итоговое вычисление `acceptance_status`. Это расходится с [интерфейсом](docs/project-review.md), строка 103: усечённый анализ не должен закрывать acceptance.

**Воспроизведение:** 103 требования с корректными source/task/check bindings и существующими отдельными файлами. Первое — обязательное L1, остальные 102 — необязательные L4. Все `file_exists` выполняются; L4 закономерно остаются OPEN. Итог:

```json
{"acceptance_status":"PASS","omitted_findings":2,"visible_findings":100,"mandatory_status":"PASS"}
```

**Причина:** статус раннего обязательного требования вычисляется до того, как поздние `HIGHER_LEVEL_NOT_VERIFIED` переполняют лимит findings. Финальный агрегатор не перепроверяет `omitted_findings`.

**Последствие:** потребитель, ориентированный на общий статус, видит PASS у неполного отчёта. Пример не доказывает ложную сертификацию L4: они остаются OPEN, а writer уже правильно отказывается применять усечённый отчёт. Нарушена именно заявленная полнота общего acceptance.

**Как исправить:** после формирования всех findings вычислять общий статус в порядке `mandatory FAIL → FAIL; любое усечение → OPEN; затем обычная агрегация`. Не превращать optional L4 в mandatory; добавить независимую проверку полноты отчёта.

**Критерий приёмки:** описанный пример даёт OPEN; перестановка требований не меняет итог; обязательный FAIL остаётся FAIL при усечении; `apply-tasks` по-прежнему не пишет такой отчёт.

### AB-03 — P2: A скрывает повреждённые доказательства пары за SKIP/exit 0

**Где:** [skill_behavior.py](tools/skill_behavior.py), строки 97–113 и 131–136.

**Воспроизведение:** подготовить два согласованных synthetic trial manifest, затем заменить SHA-256 transcript в with-rule на `000…000`. `evaluate` правильно возвращает `evidence_status=FAIL`, однако `compare` выдаёт верхнеуровневый `status=SKIP`, а реальный CLI завершается с **exit 0**. Вложенный FAIL можно увидеть только при дополнительном разборе результата.

**Причина:** `compare` интерпретирует invalid evidence как обычную несопоставимость. CLI проверяет только верхнеуровневый `evidence_status`, которого у результата пары нет, и верхнеуровневый status.

**Как исправить:** возвращать явный общий статус доказательств пары и распространять любой `evidence_status=FAIL` на неуспешный результат проверки/exit 2. Поведенческий результат при этом оставить SKIP: повреждённый файл не доказывает плохое поведение модели. Обычное отсутствие запусков или разные настройки должны оставаться SKIP.

**Критерий приёмки:** subprocess-тест пары со stale hash, недопустимым путём и некорректной структурой завершается ненулевым кодом; валидные, но несопоставимые испытания остаются SKIP/0. Это соответствует заявленной семантике exit в [протоколе испытаний](skills/verification/references/behavioral-tests.md), строки 56–59.

### AB-04 — P2: A теряет уже подтверждённый FAIL при незавершённом испытании

**Где:** [skill_behavior.py](tools/skill_behavior.py), строки 66–87.

**Воспроизведение:** корректно привязанный transcript, заполненные environment, `run_kind=agent`, именованный REVIEWED reviewer; первый checkpoint отмечен FAIL с допустимой строкой доказательства, последний — NOT_RUN без evidence. Результат: `evidence_status=SKIP`, `behavioral_status=SKIP`.

Это синтетическая проверка логики утилиты, **не реальное испытание модели**.

**Причина:** даже известный FAIL выдаётся только при `complete=True` для всего набора checkpoints. Сценарий, прерванный после уже обнаруженного нарушения, выглядит как просто неиспытанный.

**Как исправить:** отделить полноту прогона от наблюдаемого нарушения. Валидный, просмотренный FAIL конкретного checkpoint должен сохраняться при незавершённых остальных checkpoints. PASS по-прежнему требует полной совокупности доказательств. Offline, невалидный manifest и FAIL без допустимой evidence не должны становиться доказанным поведенческим FAIL.

**Критерий приёмки:** тест reviewed/evidenced FAIL + NOT_RUN сохраняет FAIL; все NOT_RUN дают SKIP; offline не даёт behavioral PASS; отсутствующая или неверная ссылка на строку не подтверждает нарушение. Согласовать агрегирование с AB-03, сохранив отдельные статусы качества доказательств и поведения.

### AB-05 — P2: запрет Skill ошибочно выбирает этот Skill

**Где:** [mcp_runtime.py](tools/mcp_runtime.py), строки 167–174; [skill_catalog.py](tools/skill_catalog.py), intent/metadata fallback в `search`.

**Подтверждённые запросы:**

| Запрос | Фактический route/search | Ожидаемый смысл |
|---|---|---|
| `Do not use blender-animation; export GLB.` | Только `blender-animation` | Export owner, без animation |
| `Не используй blender-animation; экспортируй GLB.` | Только `blender-animation` | Export owner, без animation |
| `Do not use blender-animation.` | `blender-animation` | Нет положительного запроса на этот owner |

**Происхождение:** дефект воспроизведён также на `mcp_runtime.py` из **`becd57b`**, до A. Это не новая регрессия A; это незакрытый случай в области, которую A улучшал.

**Причина:** explicit IDs извлекаются до `action_query`, затем имеют приоритет над разрешённым действием. Если просто убрать этот приоритет, metadata fallback всё ещё может повторно подобрать запрещённое имя из исходного текста.

**Как исправить:** для предложений из предложений естественного языка извлекать explicit IDs из положительных action clauses после фильтрации ограничений. Учитывать ограничения и в metadata fallback. При этом самостоятельный точный запрос `blender-animation` должен продолжать читаться как явный ID. Не делать из router механизм выдачи разрешений: результат поиска остаётся только подсказкой.

**Критерий приёмки:** RU/EN negative tests одновременно для `route_task`, `search`, `context`; разрешённый export не исчезает; чистый запрет не грузит animation; прямые положительные IDs и существующие preservation tests сохраняются.

## 6. Рекомендации по развитию

1. **Расширять тесты по переходам состояния.** Сейчас сильнее покрыты отдельные состояния и «повтор того же отчёта», чем `FAIL → PASS → FAIL`, прежний хеш после промежуточного изменения и частично выполненные проверки. Для B полезны компактные таблицы переходов; для bounded outputs — тесты около 99/100/101 findings и независимость от порядка входных записей.

2. **Уточнить общий словарь статусов без новой системы управления.** Оставить раздельными: корректность входа, завершённость анализа, принятие результата, полноту отчёта, подтверждённое поведение и visual acceptance. Для каждого CLI документировать, какие поля обязан проверить потребитель. У `project_review` exit 0 при acceptance FAIL — уже объявленный интерфейс, не ошибка; менять его молча нельзя. Ошибка AB-03 относится к другому, явно обещанному контракту `skill_behavior`.

3. **Проверять discovery на целых пользовательских фразах.** Однословные `cross-artifact`, `traceability`, `convergence` полезны, но не заменяют RU/EN запросы с запретами, сохранением данных и несколькими этапами. Зафиксировать ожидаемого owner и отсутствие лишних owners для route/search/context. Не наращивать независимые словари одних и тех же триггеров.

4. **Сохранить лёгкую архитектуру.** Разделение read-only анализа, writer и impact удачное. Не добавлять отдельный Ledger, scheduler, автоматический запуск движков или новый canonical owner для устранения этих ошибок. Новые adapters подключать только под конкретный потребительский сценарий и текущие доказательства; L1-хеш не превращать в оценку качества модели.

5. **Собирать воспроизводимый пакет поставки.** Нужны commit SHA, allowlist, версии интерфейсов, checksums, результаты clean-tree проверок и отдельный live smoke. В CI стоит запускать быстрые boundary/negative tests и полный offline suite без платных моделей и 3D-генерации. Проверки исполнения модели и визуального качества остаются отдельными явными экспериментами.

6. **Разделять принятие пользователем и измерение эффекта.** Пользовательское принятие визуального улучшения после A не пересматривается этим ревью. Контролируемая причинная оценка G5 по-прежнему не доказана. Если понадобится измерение, делать небольшой сопоставимый набор реальных trial с успешным чтением Skill и сохранённым trace; текущие unit/probe fixtures таким экспериментом не являются.

7. **Держать Pulse коротким и текущим.** Вверху — установленный HEAD, свежий результат, открытые AB-01–AB-05 и следующий шаг; подробные прежние проверки — в датированных отчётах. Это снизит вероятность принять старое «DONE» или старый интерфейс за сегодняшнее состояние.

## 7. Граница ревью

Проверены текущие файлы реализации A/B, их tests и consumers, история установки, контракты, локальная интеграция и изолированные воспроизведения.
