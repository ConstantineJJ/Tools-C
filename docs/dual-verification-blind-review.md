# Dual Verification v1 — practical blind experiment

Status: PLANNED / NOT_RUN. This instruction is not visual acceptance evidence.
Owner: user/experiment coordinator; reviewer: one independent read-only critic.
Protocol: [Verification](../skills/verification/references/dual-verification.md).

1. Select three previous AgentBlue2 versions and one previously user-approved
   control asset. Confirm actual files, canonical source/Model Contract and the
   control's approval record before starting. Never invent an approved control
   or silently choose another character. Keep prior reports/chronology private.
2. Coordinator randomly maps versions/control to A, B, C, D and stores the mapping
   separately. Hide creation order, AI/model names, version labels, filenames with
   chronology and all prior artistic evaluations. Present pixels with anonymous
   labels. If paths/contract IDs reveal origin, use a coordinator presentation
   that conceals them; do not modify the canonical contract or misstate its hash.
3. Reuse genuinely current sufficient captures, verified saved-file state and
   canonical reference. Where old versions have no trusted snapshot history,
   reopen each immutable version in an isolated disposable Blender session and
   probe/capture its state. Preserve production scene/files. No latest-revision
   label applied retrospectively to old screenshots. Record comparable pose,
   framing, projection and lighting. Render only missing/stale angles: standard
   front/side/back/three_quarter/high_45/low_45 plus needed face/hair closeups.
4. Build one batch of blind objective packets. Give the critic each candidate's
   appropriate reference/design locks, user constraints, protected zones and
   current captures. Do not give implementer artistic opinions, the mapping or
   model source names. Explicitly require real image inspection; if independent
   execution is unavailable, label SELF_REVIEW and do not count this experiment
   as an independent trial.
5. Critic returns one compact report per A/B/C/D: stage, one of four verdicts,
   0–5 evidence-backed issues with WHAT/WHERE/WHY/EVIDENCE/FIX and priority,
   approximate impact/cost/risk with rationale, PRESERVE, LEAVE_AS_IS,
   DO_NOT_CHANGE, NEXT. Confirm proportion allegations in front AND side, use
   oblique views for contact/volume, and investigate occlusion. Zero issues is
   valid. Critic edits neither asset nor approved design.
6. Freeze initial reports before disclosing mapping or prior conclusions. User
   or a separate adjudicator checks each proposed defect against actual canonical
   evidence. Mark CONFIRMED / FALSE_POSITIVE / UNRESOLVED with observed reasons.
   Check control false positives, missed substantial defects, damage risk to
   accepted regions, priority usefulness and whether insufficient evidence led
   to a capture/inspection request. Do not convert taste into a design requirement.
7. Record images opened, reviewer/dispatch IDs, packets/hashes, verdicts, adjudicated
   issues, actual review duration, number of reused/new renders, and unresolved
   criteria in existing task receipts/checkpoints. Only then reveal A/B/C/D and
   compare with earlier implementer findings. No invented similarity percentage.
8. Optional separately authorized correction experiment: select bounded confirmed
   fixes, preserve accepted regions, make needed AFTER captures, verify freshness,
   compare RESOLVED/IMPROVED/UNRESOLVED/NEW_REGRESSION and stop/reconsider after
   two failed methods or escalate after three unresolved passes. For minor
   differences the user chooses finish/polish. Save actual evidence before calling
   any visual gate PASS.

This implementation prepares the trial; it does not claim to have selected or
rendered the four candidates, dispatched an asset critic, or measured likeness,
false-positive rates, avoided render costs or artistic improvement.
